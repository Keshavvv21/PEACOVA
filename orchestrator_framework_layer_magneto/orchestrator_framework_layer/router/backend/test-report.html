Findings

real, observed — not theoretical

Enabling ak-router changed zero answers

Every prompt landed on the identical provider in both configurations — including the two that fall back to rule-based. The deterministic strategy's capability-tier ordering reproduces today's real chain behavior exactly, which is the correct result for a v1 that's supposed to be a safe swap-in, not a silent behavior change.

Both configs burn ~37s on two prompts before falling back

how many projects are there and show me my tasks hit groq (fails fast, ~75ms), then walk ollama → algo-akanade-slm-coding → algo-akanade-slm-trading — each eating the full 12s local hard timeout — before landing on the rule floor. Same in old and new: not a regression from this work, but a real, pre-existing cost worth fixing (skip unreachable local rungs faster, or reorder them behind rule for this task shape).

his-architecture's 0.8s proxy timeout is sometimes too tight

what's overdue timed out calling /api/admin/router/his-architecture/route. RouteLLM's mf router attempts a real OpenAI embeddings call before falling back to random (no funded OpenAI key exists on this deployment — see the plan's own write-up) — that failed round trip occasionally exceeds ROUTER_SERVICE_TIMEOUT_S. Worth defaulting straight to random when no real OpenAI key is configured, rather than paying for the failure every call.
